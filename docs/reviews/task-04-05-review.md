## 발견 사항

### 1 / Med / 템포 적용 이후 `getState().combo`가 이전 콤보를 반환

**문제**

템포 변경이 적용되는 비트가 시작됐지만 `resolveBeat()`가 실행되기 전에는 `getState()`가 이전 콤보를 그대로 반환합니다.

템포 업 요청의 자격 검사에는 유효 콤보 0이 적용되지만, 공개 상태 조회에서는 아직 리셋되지 않은 값이 노출됩니다.

**근거**

`src/core/combatSystem.ts`

- `effectiveCombo()`는 현재 비트 BPM과 마지막 확정 비트 BPM이 다르면 0을 반환합니다.
- `getState()`는 `effectiveCombo()`를 사용하지 않고 `this.combo.value`를 반환합니다.
- 실제 콤보 리셋은 `resolveBeat()` 내부에서 수행됩니다.

재현 조건:

1. beat 6에서 템포 업을 예약하고 콤보 6을 확보합니다.
2. beat 7을 확정하여 콤보 7을 확보합니다.
3. beat 8이 시작되고 120BPM이 적용됩니다.
4. beat 8 확정 이전에 `getState()`를 호출하면 콤보 7이 반환됩니다.
5. 같은 시점의 `requestTempoUp()`은 유효 콤보 0을 적용하여 `combo_too_low`로 거절합니다.

**명세:** §3.2, D-07(c)

**권장 조치**

템포 적용 순간부터 공개 상태와 템포 요청 자격 검사가 동일한 유효 콤보를 사용하도록 상태 갱신 시점을 일치시키는 것이 필요합니다.

### 2 / Med / `resolveBeat()`가 Good 윈도우 종료 여부를 검증하지 않음

**문제**

`resolveBeat(beat)`는 비트 순서만 검증하고 해당 비트의 Good 판정 윈도우가 실제로 닫혔는지 확인하지 않습니다.

호출자가 비트를 조기에 확정하면 이후 도착한 정상적인 Perfect/Good 입력이 전투에 반영되지 않을 수 있습니다.

**근거**

`src/core/combatSystem.ts`

```ts
if (beat !== this.lastResolvedBeat + 1) {
  throw new RangeError(...);
}
```

해당 검증 이후 현재 시각을 확인하지 않고 즉시 확정을 진행합니다.

재현 조건:

1. beat 1의 Good 윈도우가 열려 있는 상태입니다.
2. `resolveBeat(1)`이 먼저 호출됩니다.
3. beat 1의 Perfect 범위에서 공격 입력이 도착합니다.
4. 이미 확정된 비트이므로 `beat_already_resolved`가 반환됩니다.
5. 공격 피해와 콤보가 반영되지 않습니다.

**명세:** §3.3 — 판정 윈도우가 닫힌 뒤 한꺼번에 확정

현재 구현은 호출자가 정확한 확정 시각을 보장한다는 전제하에서는 정상 동작합니다. 따라서 내부 계산 오류보다는 공개 API의 사전조건이 강제되지 않는 문제입니다.

**권장 조치**

확정 가능 시각을 검증하거나 호출 계층에서 Good 윈도우 종료 및 입력 지연을 반드시 보장하도록 계약을 강화해야 합니다. 윈도우 종료 이전 확정 시도가 처리되지 않는 테스트도 필요합니다.

### 3 / Low / D-05의 템포 예약 진입점 제한이 API 수준에서 강제되지 않음

**문제**

`BeatTimeline.requestTempo(bpm, currentBeat, deferOneBar)`가 공개 메서드로 유지되어 있습니다.

현재 소스에서는 `TempoSystem`만 호출하지만, API 자체는 외부에서 임의의 `currentBeat`와 `deferOneBar`를 전달할 수 있도록 허용합니다.

**근거**

`src/core/beatTimeline.ts`

```ts
requestTempo(
  bpm: Bpm,
  currentBeat: number,
  deferOneBar = false,
)
```

`tests/tempoSystem.test.ts`는 현재 소스 파일에서 `.requestTempo(` 호출 위치를 검사하지만, 공개 API를 통한 향후 우회 호출 가능성까지 막지는 못합니다.

예를 들어 `BeatTimeline` 인스턴스를 직접 보유한 코드에서는 실제 현재 시각과 다른 미래 비트를 전달할 수 있습니다.

**명세:** D-05 — 현재 비트는 TempoSystem이 계산하며 BeatTimeline.requestTempo는 TempoSystem 전용

**권장 조치**

TempoSystem 외부에서 임의 비트를 사용한 예약이 불가능하도록 API 접근 경계를 강화하는 것이 바람직합니다.

단, 현재 `CombatSystem`의 정상 공개 경로에서는 해당 우회가 확인되지 않았으므로 잠재적 설계 위험으로 분류합니다.

### 4 / Low / 입력 순서 무관성 테스트가 동일 비트·동일 채널의 경쟁 입력을 검증하지 않음

**문제**

입력 순서 무관성 테스트는 여러 비트에 걸친 공격·회피 입력을 재정렬하지만, 동일 비트의 동일 채널에 서로 다른 판정의 입력이 경쟁하는 상황은 포함하지 않습니다.

명세 §3.1에서는 비트당 최초 공격만 처리하도록 규정하므로 동일 채널 입력은 순서에 따라 결과가 달라지는 것이 정상입니다. 따라서 이는 구현 오류가 아니라 테스트가 보장하는 범위를 명확하게 구분할 필요가 있는 사례입니다.

**근거**

`tests/combatSystem.test.ts`

현재 순서 무관성 테스트의 `inputs` 배열에는 동일 비트에 공격과 회피가 함께 들어가는 경우는 있지만, 동일 비트의 공격 Perfect와 Miss가 서로 다른 순서로 들어가는 경우는 없습니다.

**명세:** §3.1 최초 입력 규칙, §3.3 비트 확정 순서 독립성

**권장 조치**

서로 다른 비트의 입력 순서 및 같은 비트의 서로 다른 채널 순서에는 동일한 최종 결과를 요구하고, 동일 비트·동일 채널의 중복 입력에는 최초 입력 우선 규칙을 별도로 검증하는 테스트를 보강하는 것이 좋습니다.
