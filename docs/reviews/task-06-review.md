# BEAT//BREAK — Task 06 코드 리뷰

**검토 범위:** `task-06.diff`, 기획서 v0.3의 3.1절·5장, `decisions.md`의 D-05·D-07·D-08.

`src/core/` 내부 로직 및 화면 디자인은 리뷰 대상에서 제외했다. 다만 core와 연결되는 호출부의 계약 위반 여부는 검토했다.

## 1. 중점 검토 결과

| 검토 항목 | 결과 |
|---|---|
| 1. 입력 타임스탬프 → 오디오 시계 | 기본 변환식 정상, 시간축 정렬의 정밀도 위험 존재 |
| 2. 판정·확정 시각에 다른 시계 혼입 | 직접적인 위반 미발견 |
| 3. Good 윈도우 + 50ms 이후 확정 | 코드상 조건 충족 |
| 4. 템포 변경 후 메트로놈 동기화 | 예약 시각 계산 일치, 예약 누락 위험 존재 |
| 5. 재시작 시 이전 자원 정리 | 오디오 노드 및 컨텍스트 정리 미흡 |
| 6. 텔레메트리와 실제 판정 일치 | 불일치 가능 경로 확인 |

**테스트 확인 제한:** 제공된 자료에는 Vitest 테스트 코드가 있지만 `npm run test`의 실제 실행 출력은 포함되어 있지 않다. 따라서 테스트 통과 여부는 검증하지 않았으며, 아래 내용은 정적 코드 리뷰 결과다.

## 2. 발견된 문제

### 1 / High / 확정된 공격으로 인정되지 않은 입력이 성공 통계에 포함됨

**문제:** `beat_already_resolved`로 처리된 Perfect/Good 입력도 BPM별 성공 횟수와 첫 성공 시각에 반영된다.

**근거:**
- `src/telemetry/runTelemetry.ts` — diff 1115~1150행 부근.
- `COUNTED_ATTACK_KINDS`에 `beat_already_resolved`가 포함됨.
- `summarize()`는 이 결과를 실제 공격으로 인정된 `pending`과 동일하게 집계함.
- D-07(d)에 따르면 이미 확정된 비트에 도착한 Perfect/Good은 전투 상태를 변경하지 않음.

**재현 가능한 상황:** beat 1의 Good 입력이 이벤트 처리 지연으로 비트 확정 이후 전달되면, 실제 적 HP와 콤보는 바뀌지 않지만 텔레메트리에는 Good 1회가 추가될 수 있다. 이 경우 H2의 BPM별 성공률과 H3의 첫 공격 성공 시점이 실제 전투 결과와 달라진다.

**권장 조치:** 유효 공격 판정과 확정 후 무효 입력을 구분해 집계한다. `beat_already_resolved`는 진단용 이벤트로 유지하되 실제 성공률에 포함하지 않도록 한다. 해당 상황의 회귀 테스트를 추가한다.

### 2 / Med / 템포 업 가능 횟수가 실제 가능 상태 전환을 누락할 수 있음

**문제:** 템포 업 기회 집계가 `BattleSession.update()`에서만 실행되므로, 두 프레임 사이에 가능 상태로 전환되고 곧바로 템포 업을 요청하면 기회를 집계하지 못할 수 있다.

**근거:**
- `src/game/battleSession.ts` — diff 817~825행, 871~878행.
- `requestTempoUp()`은 성공한 예약을 즉시 기록하지만 `tempoWasAvailable` 상태를 갱신하지 않음.
- 가능 여부는 이후 프레임의 `update()`에서만 평가함.

**재현 가능한 상황:**
1. 콤보가 5에 도달하고 템포 업이 가능한 상태가 됨.
2. 다음 `update()` 전에 T 입력으로 템포 업을 예약함.
3. 이후 `update()`에서는 예약 대기 상태이므로 `available`이 아님.

결과적으로 `tempoSelections = 1`, `tempoOpportunities = 0`이 가능하다. D-08(c)의 정의와 일치하지 않는다.

**권장 조치:** 템포 업 요청 전후에도 가능 상태 전환을 관찰하거나, 실제 예약 성공 시 해당 기회가 집계되었는지 보장한다. 연속 프레임 사이에 입력이 들어오는 테스트를 추가한다.

### 3 / Med / 재시작·종료 시 이미 예약된 오디오 노드가 정리되지 않음

**문제:** `Metronome.stop()`은 예약용 타이머만 해제하고 이미 생성된 Web Audio 노드는 관리하지 않는다.

**근거:**
- `src/audio/metronome.ts` — diff 129~133행, 160~171행.
- `src/game/battleScene.ts` — diff 451~475행.
- 메트로놈은 클릭을 최대 100ms 먼저 예약함.
- `createClickPlayer()`는 OscillatorNode와 GainNode를 생성하지만 생성한 노드의 참조를 유지하지 않음.
- 장면 종료 시에도 AudioContext를 닫는 처리가 없음.

**영향:** 전투 종료 직전에 예약된 클릭은 `stop()` 이후에도 재생될 수 있다. 노드 자체는 정해진 종료 시각에 멈추므로 무한 재생 문제는 아니지만, 이전 판의 오디오 예약이 즉시 취소된다는 보장은 없다. 장면이 재생성되는 경우 AudioContext의 수명 관리도 불명확하다.

**권장 조치:** 예약된 오디오 노드의 참조를 관리하고 중지 시 미재생 노드를 취소하도록 한다. Scene 종료 시 AudioContext 정리 정책을 명시한다. 전투 종료 직전과 재시작 직후의 오디오 재생 여부를 테스트한다.

### 4 / Med / 메트로놈 스케줄러 지연 시 박자 소리가 누락됨

**문제:** 오디오 예약 타이머가 지연되어 비트 시각을 지나면 해당 클릭을 재생하지 않고 건너뛴다.

**근거:**
- `src/audio/metronome.ts` — diff 140~155행.
- `t >= now` 조건을 만족하지 않으면 `playClick()`이 호출되지 않음.
- 그와 관계없이 `nextBeat++`가 실행됨.
- `tests/audio.test.ts`에서 이미 지난 비트를 건너뛰는 동작을 검증하고 있음.

**영향:** 백그라운드 탭 전환이나 메인 스레드 지연으로 메트로놈 소리가 일부 누락될 수 있다. BeatTimeline의 절대 시각과 예약된 클릭의 시각이 틀어지는 것은 아니지만, 실제 들리는 리듬과 판정 진행 사이에 간극이 발생한다.

**권장 조치:** 의도된 누락 정책이라면 이를 명시하고, 재생 누락 횟수를 진단할 수 있도록 한다. 탭 복귀 및 긴 메인 스레드 정지 상황의 테스트를 추가한다. 지난 비트를 늦게 재생하는 방식은 별도 승인 없이 적용하지 않는 것이 적절하다.

### 5 / Low / 입력 타임스탬프 변환 시 두 시계를 원자적으로 읽지 않음

**문제:** 입력 시각 변환식 자체는 올바르지만, 두 시계의 현재값을 순차적으로 읽기 때문에 측정 시점 차이가 변환 오차로 들어간다.

**근거:**
- `src/audio/audioClock.ts` — diff 47~54행, 75~78행.
- `eventTimeToAudioSec()`는 두 현재 시각이 같은 순간의 값이라는 가정을 사용함.
- 호출부는 `this.ctx.currentTime`을 읽은 뒤 `performance.now()`를 읽음.

**영향:** 일반적인 실행에서는 오차가 작을 것으로 예상되지만, 메인 스레드 지연이나 오디오 시계의 갱신 특성에 따라 변환 오차가 발생할 수 있다. 특히 Perfect/Good 경계 주변의 입력에 영향을 줄 가능성이 있다.

**권장 조치:** 가능한 환경에서 `AudioContext.getOutputTimestamp()` 등을 이용한 시계 대응 관계를 검토하고, 변환 오차를 측정한다. 단순 단위 테스트뿐 아니라 실제 브라우저에서 시간축 정렬을 검증한다.

## 3. 추가 검증 결과 — 명세 위반 미발견

**입력 시각 변환:** `audioNowSec - (perfNowMs - eventTimeStampMs) / 1000`의 부호와 ms→초 변환이 올바르다. 이후 `originSec`을 차감하고 core에서 캘리브레이션 오프셋을 처리하는 구조도 명세와 부합한다.

**판정·확정 시계:** `BattleScene.update()`는 Phaser의 프레임 델타 대신 오디오 시계에서 현재 시각을 계산한다. `setTimeout`은 메트로놈의 미래 오디오 예약 작업에 사용되며 `Date`는 기록용으로 사용된다. 제공된 diff에서 이 값들이 공격 판정 시각으로 직접 혼입되는 경로는 발견하지 못했다.

**비트 확정 조건:** `BattleSession.update()`는 `t_now + t_offset > t_beat + (W_Good + ε + 50) / 1000`이 성립할 때만 확정을 진행한다. 경계가 같으면 확정하지 않으므로 D-08(a)의 윈도우 종료 및 여유 시간 조건과 일치한다.

**템포 변경 동기화:** 메트로놈은 매 예약 시 `session.combat.beatTime(beat)`를 사용한다. 고정된 초기 BPM으로 다음 클릭 시각을 계산하지 않으므로, 템포 변경 이후의 비트 시각이 반영되는 구조다. 다만 실제 브라우저 오디오 출력의 정밀도까지 입증한 것은 아니다.

**재시작 시 전투 상태:** 새로운 `BattleSession`을 생성해 CombatSystem과 RunTelemetry를 교체한다. 이전 판의 콤보·HP·텔레메트리가 새 판에 그대로 재사용되는 경로는 발견하지 못했다.
