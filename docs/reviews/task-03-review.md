# BEAT//BREAK — Task 03 코드 리뷰 결과

**검토 범위:** `task-03.diff`, `BEAT_BREAK_v0.3.md` §3.1·§3.2 템포 적용 시점·§3.5, `decisions.md` D-04·D-06  
**테스트 결과:** 3개 파일, 130개 테스트 통과(제공된 실행 결과 기준).  
**요약:** 확정된 구현 결함 0건 / Med 1건 / Low 3건

제공된 diff에서 명세와 직접 충돌하는 구현은 발견되지 않았다. 다만 테스트가 검증하지 않은 경계 조건 4건을 확인했다. 아래 항목은 **확정된 버그가 아닌 검증 누락 및 잠재 위험**이다.

## 문제 목록

### 1 / Med / 120→140 BPM 전환 경계 테스트 누락

**문제**  
템포 변경 테스트가 100→120 BPM 전환만 검증한다. 120→140 BPM으로 전환하는 경우의 새 판정 윈도우 적용 여부는 확인되지 않았다.

**근거**  
`tests/rhythmJudge.test.ts`의 템포 경계 테스트는 `requestTempo(120, 6)`만 사용한다.

140 BPM의 Perfect ±60ms, Good ±110ms가 전환 직후 적용되는지는 검증하지 않는다.

**권장 조치**  
120→140 BPM 전환 시 다음 경계 비트에서 ±60/61ms, ±110/111ms를 확인하고, 경계 직전 비트는 120 BPM 윈도우를 유지하는지 검증한다.

---

### 2 / Low / 판정 윈도우 경계 바로 안쪽 테스트 누락

**문제**  
Perfect/Good 경계값과 경계 바깥쪽 1ms는 검증하지만, 경계 안쪽 1ms는 검증하지 않는다.

**근거**  
현재 벡터는 다음 값만 포함한다.

| BPM | Perfect 경계 | Good 경계 | 누락된 안쪽 값 |
|---|---|---|---|
| 100 | 90 / 91ms | 160 / 161ms | 89 / 159ms |
| 120 | 75 / 76ms | 135 / 136ms | 74 / 134ms |
| 140 | 60 / 61ms | 110 / 111ms | 59 / 109ms |

현재 코드의 `<=` 비교는 명세와 일치한다. 그러나 내부 경계 테스트가 없어 향후 비교 연산자 변경 시 회귀 검출이 약해질 수 있다.

**권장 조치**  
각 BPM에서 경계 안쪽 1ms를 양방향으로 추가 검증한다.

---

### 3 / Low / 음수 캘리브레이션 오프셋의 판정 방향 검증 누락

**문제**  
양수 오프셋의 적용 방향은 검증하지만 음수 오프셋이 실제 판정을 반대 방향으로 이동시키는지는 검증하지 않는다.

**근거**  
`src/core/rhythmJudge.ts`

```ts
const correctedSec = inputSec + this.offsetMs / 1000;
```

구현은 §3.1의 덧셈 규칙과 일치한다.

다만 테스트는 `+50ms`에 집중되어 있고, `-200ms`는 설정 가능 여부만 확인한다.

**권장 조치**  
`-50ms` 적용 시 비트보다 50ms 늦은 입력이 오차 0ms로 보정되는지 확인한다. 오프셋으로 인해 가장 가까운 비트 배정 자체가 바뀌는 경우도 추가 검증한다.

---

### 4 / Low / D-06 허용 오차의 경계 확장 검증 누락

**문제**  
`JUDGE_EPS_MS = 1e-6` 적용 자체는 승인된 D-06과 일치하지만, 허용 오차로 인해 실제 경계가 얼마나 확장되는지 테스트하지 않는다.

**근거**

```ts
if (absErr <= PERFECT_WINDOW_MS[bpm] + JUDGE_EPS_MS)
```

D-06에 따라 100 BPM에서 오차가 `90.0000005ms`이면 Perfect로 판정된다. 이는 승인된 1e-6ms 허용 오차 내부이므로 **구현 결함은 아니다.**

다만 허용 오차를 초과하는 값이 반드시 하위 판정으로 이동하는지 확인하는 테스트는 없다.

**권장 조치**  
각 경계에 대해 `window + 0.5e-6ms`와 `window + 2e-6ms` 같은 값을 검증한다. 부동소수점 계산 오차를 고려하여 실제 판정에 사용되는 `errorMs`도 확인한다.

## 최종 판정

**Task 03: 구현 결함 미발견, 테스트 보강 권장.**

이번 diff의 `RhythmJudge` 구현은 검토 대상 명세와 일치한다. 특히 Miss 이후 duplicate 처리, 채널별 독립성, 오프셋 덧셈 방향, BPM별 판정 윈도우 선택에서 명백한 오류가 없다.

단, `BeatTimeline.nearestBeat`의 D-04 중간값 처리까지 완전 검증했다고 판단할 수는 없다. 해당 구현은 이번 diff에 포함되지 않았기 때문이다.

**권장 우선순위:** 1번을 먼저 검증하고, 2~4번은 회귀 테스트 보강 항목으로 처리한다. 코드를 변경해야 한다고 확정할 만한 문제는 현재 발견되지 않았다.
