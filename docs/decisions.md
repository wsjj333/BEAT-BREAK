## D-01 적 공격 비트는 회피 전용 (2026-11-16)
- **결정:** 적 공격 비트(beat 4, 8, 12, ...)에서는 공격 입력을 무시하고 회피만 처리한다. 회피 성공(Perfect) 시 콤보 유지, 회피 실패(Good/Miss/미입력) 시 피해 1, 콤보는 유지한다.
- **근거:** v0.3 3.3절의 41행(둘 다 입력 시 회피 우선)과 42행(공격은 적 공격이 없는 비트에서만 처리)이 충돌. "공격 비트 / 회피 비트"로 역할을 나누는 쪽이 규칙 설명이 단순해 H3(이해 가능성)에 유리하다고 판단.
- **변경 조건:** 플레이테스트에서 회피 비트를 "쉬는 박자"로 느껴 긴장감이 떨어진다는 피드백이 2명 이상이면 재검토.
- **미결:** 회피 실패 시 콤보 리셋 여부 → MVP는 유지. H2 관찰 후 결정.

## D-02 밸런스 사전 예측 (2026-11-16)
- **예측 1 — 전투가 짧다:** 적 HP 300 ÷ 100 BPM Perfect 피해 12.5 = 24타. 회피 비트 포함 약 32비트(약 20초)에 전투 종료. 템포 업 기회가 1~2회뿐이라 H1(자발적 선택) 관찰이 어려울 수 있음.
- **예측 2 — 초보자가 먼저 패배:** 플레이어 HP 5, 4비트마다 적 공격 → 회피 전부 실패 시 20비트(100 BPM 약 12초)에 패배. H3 "30초 이내 첫 정박 성공"보다 패배가 먼저 올 수 있음.
- **검증 방법:** 11/19 시뮬레이션 + 플레이테스트(전투 시간, 패배 시점, 템포 업 횟수).
- **수정 후보:** (a) 적 HP 600 (b) 적 공격을 beat 16부터 시작(첫 4마디 연습 구간) (c) 둘 다.
- **지금 수정하지 않는 이유:** 예측을 데이터로 확인한 뒤 바꿔야 변경 근거가 생긴다.

## D-03 Bpm 유니온 타입과 비트 번호 검증 범위 (2026-11-16)
- **결정:** BPM은 `type Bpm = 100 | 120 | 140`으로 타입 제한. 비트 번호 검증은 BeatTimeline 진입점에서만.
- **근거:** 명세에 없는 오류 처리 규칙을 만들지 않고 타입으로 잘못된 입력 차단 (리뷰 #5)
- **변경 조건:** BPM 단계가 추가되면 유니온 타입 확장

## D-04 nearestBeat 중간값 판정: 이전 비트 선택 (2026-11-16)
- **결정:** 두 비트의 정확한 중간 시점에서 nearestBeat 호출 시 이전(낮은) 비트를 반환한다. 부동소수점 오차 흡수를 위해 1e-9초(MIDPOINT_EPS_SEC) 허용 오차를 적용한다.
- **근거:** 기획서에 중간값 판정 규칙이 없으므로, 일관된 동작을 위해 "이전 비트 선택" 규칙을 채택. EPS는 IEEE 754 배정밀도 부동소수점의 실질적 오차 범위(~1e-15)보다 충분히 크면서 판정 윈도우(60ms 이상)보다 무시할 수 있는 크기.
- **변경 조건:** 판정 로직 구현(태스크 3) 시 다른 규칙이 필요하면 재검토.

## D-05 템포 요청 시 현재 비트는 TempoSystem이 계산 (2026-11-16)
- **결정:** 템포 요청 시 현재 비트는 호출자가 넘기지 않고 TempoSystem이 nowSec(오디오 시계)에서 계산. BeatTimeline.requestTempo는 TempoSystem 전용.
- **근거:** 리뷰 #2. 호출자가 미래 비트를 넘기면 대기 중 예약을 우회할 수 있음.
- **적용:** 태스크 4에서 구현. 이번에는 코드 변경 없음.

## D-06 판정 윈도우 경계 비교 허용 오차 (2026-11-17, 승인)
- **결정:** RhythmJudge의 윈도우 비교를 `|errorMs| <= window + JUDGE_EPS_MS(1e-6ms)`로 한다.
- **근거:** 3.1 "경계값 포함(<=)"을 지키기 위함. 예: 100BPM→120BPM 전환 후 beat 8(4.8s) +75ms 입력은 부동소수점 계산 시 errorMs = 75.00000000000017이 되어, 허용 오차가 없으면 Perfect가 아닌 Good으로 판정된다. 1e-6ms = 1e-9초로 D-04(MIDPOINT_EPS_SEC)와 동일 크기이며 테스트 벡터의 1ms 간격보다 충분히 작다.
- **변경 조건:** 입력 타임스탬프 정밀도가 1e-6ms 수준의 차이를 의미 있게 구분해야 하는 경우(현실적으로 없음).

## D-07 태스크 4+5 구현 세부 규칙 (2026-11-17, 승인)
기획서가 정하지 않은 세부 동작. (a)(c)(d)(e)(f)(g)는 제안대로 승인, (b)는 원안 기각 후 대안 채택.
- **(a) "현재 비트" = 이미 시작된 가장 최근 비트(내림).** `BeatTimeline.currentBeatAt(nowSec)`. 반올림(nearestBeat)이면 beat 7.6에서의 요청이 "beat 8"로 계산되어 사실상 미래 비트 기준 예약이 된다(D-05 취지와 충돌). 내림이면 적용 비트는 항상 현재 시각보다 미래다. 부동소수점 오차는 MIDPOINT_EPS_SEC(1e-9초)로 흡수.
- **(b) 다음 마디 경계 비트의 Good 윈도우가 이미 열린 뒤의 요청은 그다음 마디 경계로 예약한다.** Good 윈도우는 현재 BPM 기준, 경계 포함(`<=`). 예: 100BPM에서 beat 8 시각 −161ms 요청 → beat 8 적용, −160ms 요청 → beat 12 적용. 입력 판정은 입력 시 결과를 그대로 사용한다(확정 시 재판정 없음).
  - **근거:** 화면 판정과 실제 결과의 불일치 방지(H3). 원안(오차를 저장해 확정 시 새 BPM으로 재판정)은 "Perfect로 보였는데 피해"가 생길 수 있어 기각.
  - **보장:** 이미 판정된 입력이 속한 비트의 BPM은 이후 바뀌지 않는다. Good 윈도우가 열리기 전 그 비트에 배정된 입력은 Miss뿐이고, BPM이 올라 윈도우가 좁아져도 Miss로 남는다.
  - **윈도우 열림 판단은 오프셋 보정 시각 기준 (입력 판정과 같은 시간축).** 보정 시각 = nowSec + 캘리브레이션 오프셋. 오프셋 없이 판단하면 +200ms 설정에서 이미 판정된 입력의 BPM이 바뀌는 경로가 남는다.
  - **구현:** 연기 시 `BeatTimeline.requestTempo(bpm, currentBeat, deferOneBar=true)`로 적용 비트만 한 마디 뒤로 미루고, 대기 중 판정(pending)은 실제 currentBeat 기준이다.
- **(c) 적용 비트가 시작됐지만 확정 전이면 유효 콤보 0.** 3.2 "적용되는 순간 콤보 0". 확정(resolveBeat)은 Good 윈도우가 닫힌 뒤라서, 그 사이 템포 요청이 옛 콤보로 통과하는 것을 막는다.
- **(d) 확정 후 도착한 입력.** 공격 Miss는 콤보만 0(`late_miss_combo_reset`), 그 외는 상태를 바꾸지 않는다(`beat_already_resolved`).
  - **해석:** 3.3의 "상태 변경 중지"는 승패 확정 후를 뜻하며 비트 확정과 무관하다. 윈도우가 닫힌 뒤 도착한 늦은 Miss의 콤보 리셋은 3.2 "Miss 시 0"에 따른 정상 동작이다.
- **(e) timeout 시점.** 0-based 비트이므로 "최대 120비트" = beat 0~119. beat 119 확정 후 승패가 없으면 timeout. beat 119에서 적 HP 0이면 승리가 우선.
- **(f) resolveBeat 순서 강제.** 0, 1, 2, ... 순서가 아니면 RangeError. 순서가 어긋나면 템포 적용 비트의 콤보 리셋이 누락될 수 있다.
- **(g) 거절 사유 우선순위.** finished → combo_too_low → at_max → pending.
- **변경 조건:** (b)로 "늦게 누른 템포 업이 한 마디 더 늦게 적용된다"는 혼란이 플레이테스트에서 보이면, 예약 비트를 UI에 미리 표시하는 안을 검토. (AI 제안, 승인)

## D-08 태스크 6 연결 세부값 (2026-11-17, 제안 — 미승인)
기획서에 없는 값·해석. 승인 전까지 아래 초기값으로 동작한다.
- **(a) 비트 확정 입력 지연 여유 `RESOLVE_MARGIN_MS = 50` (`src/core/config.ts`).** resolveBeat는 보정 시각(nowSec + 오프셋) 기준 `Good 윈도우 + JUDGE_EPS_MS + 50ms`가 지난 뒤 비트 순서대로 호출한다(`src/game/battleSession.ts`).
  - **근거:** 3.3 "판정 윈도우가 닫힌 뒤 한꺼번에 확정". 키 이벤트는 발생 시각(timeStamp)보다 늦게 처리되므로, 윈도우 정각에 확정하면 윈도우 안에서 눌렀지만 늦게 도착한 입력이 `beat_already_resolved`가 되어 HP에 반영되지 않는다. 50ms는 60Hz 기준 약 3프레임.
  - **부작용:** HP 반영이 시각 피드백보다 Good 윈도우+50ms(100BPM 210ms) 늦다. 템포 적용 비트의 확정 전 구간(D-07c 유효 콤보 0)이 50ms 길어진다.
  - **변경 조건:** 플레이 로그에서 `beat_already_resolved` 중 Perfect/Good이 관찰되면 증가, HP 반영 지연이 어색하다는 피드백이면 감소 검토.
- **(b) 시작 대기 `START_LEAD_IN_SEC = 1.0`초 (`src/game/battleScene.ts`, 표시·오디오 기술값).** 클릭/재시작 후 1초 뒤가 beat 0. 오디오는 미래 시각에만 예약할 수 있어서 필요. beat 0 = 전투 시작 기준이라는 규칙은 그대로.
- **(c) 텔레메트리 "템포 업 가능 횟수"(4장 H1) = 템포 업 가능 상태로 바뀐 횟수.** 가능 = 진행 중 · 시작 후 · 유효 콤보 5 이상 · 최대 BPM 아님 · 예약 대기 없음. 가능 상태가 유지되는 동안은 1회로 센다. "선택 횟수" = 실제 예약된 요청 수.
- **(d) 캘리브레이션 오프셋 변경은 다음 판부터 적용.** `CombatSystem`에 진행 중 오프셋 변경 API가 없고 태스크 6은 core 수정 금지라서, `[ ]`로 바꾼 값은 다음 `CombatSystem` 생성 시 적용된다. 판 중간 변경이 필요하면 core API 추가 + D-07b(윈도우 열림 판단)·resolveBeat 가드와의 상호작용 검토가 필요.
